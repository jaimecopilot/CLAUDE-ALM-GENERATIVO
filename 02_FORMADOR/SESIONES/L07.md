# Guion L07 — Pipeline GitLab CI/CD y diagnóstico (75 min)

## Qué se aprende
No confundir ALM generativo con CI/CD: el primero orquesta las fases; el segundo ejecuta comprobaciones y entrega mediante GitLab Runner.

## Minutaje
- 000–010: stages, jobs, runner, MR y artefactos.
- 010–020: definir contrato CI y preparar prompt operativo.
- 020–035: Claude genera .gitlab-ci.yml; inspección colectiva.
- 035–060: push, ejecución en GitLab y consulta de logs reales.
- 060–070: reparación mínima y nuevo pipeline si falla.
- 070–075: evidencia, gate y entrega local.

## Frase que debe quedar clara
«Una configuración YAML no es un pipeline ejecutado. Podemos revisar sintaxis y comandos, pero hasta que GitLab lo lance no hay evidencia remota».

## Demostración
Abre una MR de ejemplo real del grupo, señala el pipeline asociado, estado de jobs y cómo leer log. Explica por qué un job de tests debe salir con código de error si una aserción falla. Si el YAML usa un paquete que no está instalado, muestra cómo se reconoce el fallo en el log.

## Fallos típicos
- **No hay runner**: bloqueo de infraestructura, no bug de código.
- **requirements incorrectos**: actualizar dependencias y rerun con evidencia.
- **pytest no descubre tests**: comprobar rutas.
- **GitLab job «verde» con pruebas deshabilitadas**: rechazo del gate.
- **Claude propone GitHub Actions**: rechazar por plataforma equivocada.
- **Claude propone despliegue cloud**: fuera de alcance.

## Preguntas de comprobación
¿El pipeline CI hace análisis de requisitos? No. ¿Qué es una MR? Propuesta de integración revisable, no equivalente a commit. ¿Qué evidencia muestra que CI pasó? Enlace y logs reales, no la afirmación de Claude.

## Gate
Un pipeline remoto verificado o bloqueo formal explícito, MR vinculada y comandos documentados. Guardar artefacto o informe de entrega; no presentarlo como despliegue productivo.
